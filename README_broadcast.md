# Фоновое обновление кэша без координатора

Изменения относительно `src(20261102-092117).zip`. Проверено на Flink **1.20.3**, Java 17.

## Поведение

1. Единственный `CacheSnapshotSource` читает уведомления Kafka, загружает полный bundle указанной эпохи и сохраняет bundle вместе со следующим Kafka offset в своём состоянии.
2. `CacheBundleEnvelope` кодирует bundle на ветке кэша. Обычный `broadcast()` доставляет его всем processing subtasks. Данные включают байткод, справочники, политики, версии и handler.
3. Каждый `RulesProcessingOperator` передаёт декодирование, проверку checksum, создание ClassLoader, объектов правил и индексов одному фоновому потоку. Пока он работает, сообщения обрабатываются на прежнем runtime.
4. По завершении фоновый поток ставит короткое действие в mailbox Flink. Действие публикует `RuntimeEpoch` одной заменой `AtomicReference`. Managed state и output доступны только из потока оператора.
5. `RulesProcessingFunction` получает ссылку на `RuntimeEpoch` один раз в начале сообщения. Выбор handler, локальная обработка ответа и локальный аудит используют один snapshot. Внутри сообщения смесь версий невозможна. Состояние внешнего .NET-сервиса этим механизмом не управляется.

Пользовательский `OperatorCoordinator`, команды PREPARE/READY/ACTIVATE и ожидание checkpoint для активации удалены. Локальный двухвходовый оператор оставлен для доступа к mailbox: он позволяет публиковать результат фоновой работы и выпускать стартовый буфер, даже если новых входных сообщений больше нет.

Очередь подготовки ограничена по числу версий: одна версия строится, дополнительно запоминается только самое новое обновление. Например, при подготовке N+1 поступили N+2 и N+3 — после завершения подготовки будет строиться N+3. Если runtime уже есть, устаревший результат N+1 не публикуется. Каждое обновление содержит полный кэш, поэтому пропуск промежуточной версии допустим.

## Checkpoint и восстановление

Используется обычный **общий checkpoint Flink job с одним checkpoint ID**. Отдельных checkpoint на каждый subtask код не запускает. При этом общий checkpoint может содержать активную эпоху N у одного subtask и N+1 у другого: это соответствует принятому допущению о локальной активации.

| Где | Имя state | Содержимое |
| --- | --- | --- |
| CacheSnapshotSource | `cache-source-state-v1` | Полный последний опубликованный bundle, следующий Kafka offset и сведения о незавершённой загрузке |
| Processing subtask | `cache-local-active-v1` | Полный bundle локальной активной эпохи |
| Processing subtask | `cache-local-requested-v1` | Полный новейший полученный bundle, если он ещё не активирован |
| Processing subtask | `cache-startup-pending-v1` | Сообщения, ожидающие первого готового runtime |

Состояние сохраняется как operator ListState. Локальные активные версии намеренно могут различаться, поэтому они не записываются в общий BroadcastState с требованием одинакового содержимого. ClassLoader, Future и экземпляры правил не сериализуются: при восстановлении runtime заново собирается из сохранённого байткода и справочников, без чтения кэша через API.

Checkpoint не ждёт завершения фоновой подготовки. Ссылки на активный bundle и runtime меняются в одном mailbox-действии, между сообщениями и вызовами snapshotState. Например, если checkpoint сохранил active=N, requested=N+1, после сбоя сначала восстанавливается N, затем N+1 готовится и активируется фоново. Источник также повторно распространяет свой восстановленный bundle. Дубликаты/старые эпохи не откатывают активную версию.

При изменении parallelism оператор выбирает новейший полный bundle из назначенных ему элементов ListState. Subtasks, которым локальный bundle не достался, получают его от восстановленного источника через broadcast.

Это не закрепляет версию кэша за сообщением между повторными попытками: после сбоя повторно доставленное сообщение может обработаться на другой эпохе. Гарантия одной версии относится к одной попытке полной обработки сообщения.

## Bootstrap и первое сообщение

- Если восстановленного bundle нет, CacheSnapshotSource загружает `latest` через существующий bootstrap. Это работает и при выключенном checkpoint.
- При наличии bundle в восстановленном состоянии повторный bootstrap не нужен. Явное восстановление из savepoint также использует сохранённый кэш, даже если периодические checkpoint отключены.
- Старый параметр `cache.bootstrap.enabled=false` при отсутствии восстановленного bundle игнорируется с предупреждением: обработка без первого полного кэша не начинается.
- Kafka-позиция фиксируется до bootstrap, чтобы уведомления, пришедшие во время загрузки, затем были прочитаны. Сохранённое ограничение источника: topic обновлений должен иметь **ровно одну partition**, parallelism источника кэша — 1. Parallelism обработки сообщений может быть больше 1.
- До первой готовности runtime сообщения помещаются в ограниченный буфер; после подготовки он выпускается через mailbox без ожидания следующего сообщения или checkpoint. При переполнении буфера task завершается с ошибкой. Буфер не заменяет гарантии доставки MQ.

Настройки буфера на subtask:

```properties
parallelism.process=3
cache.startup.max-pending-messages=100000
cache.startup.max-pending-bytes=67108864
```

Старые `cache.activation.max-pending-messages` и `cache.activation.max-pending-bytes` поддерживаются как fallback. Новые параметры имеют приоритет.

При обычном обновлении готового кэша ожидания нет. При первом запуске, восстановлении после падения и перезапуске task время на построение первого runtime необходимо.

## Настройки и эксплуатация

Checkpoint, restart strategy, HA, S3 и state backend продолжают задаваться конфигурацией кластера. Job не переопределяет их и допускает запуск без checkpoint. Для восстановления состояния после сбоя checkpoint должен быть включён и хотя бы один checkpoint должен успешно завершиться.

В HA-восстановлении Flink выбирает завершённый checkpoint данного job. Новый ручной запуск job сам по себе не сканирует каталог S3 в поисках «последнего»: для продолжения состояния при повторной подаче укажите restore path через `-s`. Если job запускается без восстановленного состояния, выполняется bootstrap.

Сохранение полного operator state и передача большого bundle остаются затратами CPU, памяти, сети и S3. RocksDB incremental checkpoints не превращают этот ListState в инкрементальные RocksDB SST-файлы. Новая схема убирает ожидание подготовки и общей активации из пути сообщений, но не устраняет обычные расходы checkpoint, GC и backpressure. На subtask одновременно могут существовать старый runtime, строящийся runtime и байты новейшего ожидающего bundle. Загрузка нового кэша может конкурировать с обработкой за CPU и память.

Ошибка подготовки актуальной версии не публикует частичный snapshot и передаётся в Flink как ошибка task. Ошибка уже вытесненной версии не мешает попытке подготовить новейшую. При закрытии task executor прерывается без ожидания; поздняя callback не может активировать runtime. Конструкторы правил должны завершаться и не запускать неуправляемые долгоживущие потоки.

Метрики оператора: `cacheActiveEpoch`, `cacheRequestedEpoch`, `cachePreparationInProgress`, `cachePendingMessages`, `cacheProcessingEnabled`.

## Что изменено

| Класс | Изменение |
| --- | --- |
| `Main` | Kafka cache source → encode → broadcast → локальный оператор; запуск без checkpoint разрешён |
| `CacheBundleEnvelope` | Передача полного сериализованного bundle и его идентификаторов |
| `operators/RulesProcessingOperator` | Фоновая подготовка, mailbox-публикация, локальный checkpoint state, восстановление и стартовый буфер |
| `operators/RulesProcessingOperatorFactory` | Создание локального оператора с mailbox, без координатора |
| `RuntimeEpoch` | Единый объект snapshot + handler |
| `RulesCacheRuntime` | Атомарная ссылка на RuntimeEpoch |
| `RulesProcessingFunction`, `MessageProcessingService` | Один захват snapshot на всё сообщение |
| `CacheSnapshotSource` | Обязательный bootstrap при отсутствии восстановленного bundle |

Удалены весь пакет `coordination`, `RulesReloadBroadcastProcessFunction` и `HandlerRoutingState`. При копировании файлов поверх проекта обязательно удалите эти старые классы; удобнее применить приложенный patch. Код MQ/Artemis, ACK/commit/rollback и механизм аудита не менялись.

## Переход со старой схемы

Сохранены UID `cache-snapshot-source-v1` и `process-with-cache-bundle-v1`, формат состояния источника и старого стартового буфера. Предусмотрено чтение legacy `cache-bundle-broadcast-v1[active]` при отсутствии нового локального active state.

Однако изменились topology/сетевой тип обновлений (`CacheBundleState` → `CacheBundleEnvelope`) и удалён coordinator. **Совместимость с checkpoint/savepoint вашей старой сборки целиком не проверена.** Для перехода используйте сохранённый savepoint и заранее проверьте его восстановление новой сборкой на стенде; не рассчитывайте на совместимость старого unaligned checkpoint с сохранёнными сетевыми данными прежнего типа. Не включайте пропуск невосстановленного состояния только ради успешного старта без проверки, какие данные будут потеряны.

Проверенное восстановление в тестах относится к checkpoint, созданному новой схемой. После перехода проверьте на стенде завершение checkpoint в вашем S3, рестарт TaskManager при недоступном API и дальнейшее поступление Kafka-обновлений. HA с ZooKeeper и реальные внешние сервисы в локальный тестовый стенд не входили.
